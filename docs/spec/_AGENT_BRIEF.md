# 规格编写须知（所有子 agent 必读）

## 1. 你在做什么
把 [设计文档 v0.1](../design_doc_v0.1.md)（总纲）细化成**可以直接实现**的系统规格。目标：一个能力很弱的 AI agent，只读你写的规格和任务卡，不提问，也能正确实现。

## 2. 前提（已定，不要改）
- **设计总方针**：见总纲第 0 节。拟真和游戏性的平衡点 = 战争之人 / Call to Arms / Wargame / WARNO。每个拟真机制都必须换来一个玩家决策或可见反馈，否则抽象掉。**硬核在选择，不在操作。数字要透明。**
- **技术栈**：Godot 4 + C#。模拟核心是一个**不依赖引擎**的 C# 类库（可以脱离 Godot 运行和测试），固定步长、随机种子可复现（总纲第 21 节第 1 项、9.3 节 ④）。
- **平台**：PC（Steam）。
- **路线**：阶段 0 编制试验场 → 阶段 1 MVP（纳卡战区：亚美尼亚、阿塞拜疆含纳希切万；开局 2010 年和 2020 年 9 月；双方可玩）→ 阶段 2 俄乌 → 阶段 3 海军和全球。**规格以阶段 0 和阶段 1 为准写到最细**；阶段 2、3 的内容只需要留出扩展点，标明“阶段 2+”。
- **语言**：规格正文用中文；数据结构、接口、字段名、枚举值用英文（C# 风格：类型 PascalCase，字段 camelCase，数据文件 id 用 snake_case）。
- 已有数据约定：见 [data/README.md](../../data/README.md)（单位后缀 `_km`、`_kg` 等；`confidence` 字段；不臆造数值）。

## 3. 规则
1. **先读** `docs/spec/00_glossary.md`（术语表）。术语、ID、单位一律按它来。需要新术语时，在你的文件末尾“新增术语”一节列出，不要直接改术语表。
2. **只写你负责的文件**。不要修改 `design_doc_v0.1.md` 和别人负责的规格文件。
3. **遇到总纲没定的设计问题，不要自己拍板**。写成：`🟡 建议：……  理由：……  备选：……`，并汇总到文件末尾的“待确认决策”一节。总纲里已经标 ✅ 的，直接照着写；标 🟡 的，可以采用，但也要列进“待确认决策”。
4. **数值**：每个常数都要给出初始值、单位、调参范围，以及来源或理由（真实数据、估算、平衡需要）。不确定的写 `confidence: estimated`。
5. **不要写游戏代码**。伪代码可以写，而且要写，用接近 C# 的风格。
6. 写完后，自查：有没有哪一步，弱 agent 读了以后还要猜？有就补上。

## 4. 每个规格文件的固定结构
```text
# NN 系统名
## 1. 目标与范围         这个系统解决什么问题；阶段 0 / 1 包含什么，不包含什么
## 2. 玩家能做什么、看到什么   决策清单 + 反馈清单（对应总方针第 1、3 条）
## 3. 数据结构            C# 风格的类型定义（英文），每个字段的含义、单位、取值范围
## 4. 算法与公式           按执行顺序写，每一步都要有公式和伪代码
## 5. 常数表              名称 | 初始值 | 单位 | 调参范围 | 来源/理由
## 6. 与其他系统的接口      输入谁的什么数据、输出给谁；调用时机和频率
## 7. 边界情况            除零、空集合、单位全灭、同时发生的事件等怎么处理
## 8. 测试用例            至少 5 个，给出具体输入和期望输出（数值）；能手算的尽量手算
## 9. 验证建议            哪些地方需要用 Python 脚本做数值验证（对应计划里的 V1–V7）
## 10. 待确认决策          🟡 列表
## 11. 新增术语
```
